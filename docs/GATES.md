# The gates

Three gates stand between a claim and a match. Each one is stricter than
the one before it, and each one answers a different question.

## 1. The body gate

**Question:** does the compiled body reproduce the retail bytes of this
function, at this address?

* the candidate is compiled with the qualified toolchain and the qualified
  options;
* the object is linked at the measured address;
* every byte of the function's range is compared with the retail bytes;
* the comparison covers the whole function, not a prefix.

A body that passes the body gate is a **candidate**. It is not yet counted.

## 2. The placement gate

**Question:** does the body hold at every place the game puts it?

A function can be instantiated more than once: in a table, in a loop, in a
different module. Every placement that the review covers must own its
retail bytes, and no two placements may own the same range.

The placement table lives in `config/` and is generated by the tooling, not
by hand.

## 3. The complete-program gate

**Question:** does the whole program still match?

The complete build is compared with the retail program, byte for byte, and
its hash with the pinned retail hash. Only this gate promotes a body into
the project's count.

Until a PPU compiler and its options are qualified, this gate is **closed**.
That is a fact about the project, not a failure of a particular attempt, and
it is why no percentage is published: see `docs/STATE.md`.

## What a closed gate means for the work

The gates are not a reason to stop. They are the order of the work:

* the body gate teaches what the compiler does with a given source, which is
  what every later step needs;
* the placement gate teaches what the game does with the function, which is
  what the naming needs;
* the complete-program gate is the only thing that can be called a match.

A claim that does not pass a gate is written down as what it is: an
attempt, a measurement, a hypothesis.

## Re-opening a source

Every source carries the condition that re-opens it: if the toolchain or
the options ever change, the comparison has to be run again before the
body is counted.  `tools/verify_sources.py` makes that condition
executable — it reads the address, the options and the callees each
source declares, compiles it, links it at its retail address and compares
the bytes:

```sh
python tools/verify_sources.py --elf work/eboot/EBOOT.elf \
    --toolchain /path/to/the/toolchain --image ps3gcc-toolchain
```

It needs the SDK's compiler, which the repository never ships (see
[LEGAL.md](../LEGAL.md)).
