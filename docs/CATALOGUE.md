# The function catalogue

The retail executable is stripped, so the project has no symbol table to
start from. The catalogue is the project's own answer to "where are the
functions?", and it is built from evidence: every address in it carries the
reason why it is there.

The catalogue lives in [`config/functions.tsv`](../config/functions.tsv) and
is generated by [`tools/ppu_funcs.py`](../tools/ppu_funcs.py). It holds
research metadata only — addresses and the evidence for them — never game
bytes.

## The two methods

### Prologue scan

The PS3 SDK's PPU functions open with a fixed shape: the frame is set up
with `stdu r1, -N(r1)` and the link register is saved with `mflr rX`. The
two instructions appear in both orders, and the frame size varies, so the
scanner matches the instruction words, not a fixed byte sequence.

The scan is cheap and it has no false negative on a function that follows
the SDK's shape, but it has false positives: a function that manipulates
the stack pointer in the middle of its body looks like a prologue.

### Call scan

Every `bl` names an address the program calls. The scan collects the
targets, which gives a second opinion about where the functions are — and
it also shows its own weakness: the compiler generates calls to *blocks*
inside a function (shared epilogues, jump-table targets), so a call target
is not necessarily a function start.

## What is published

`config/functions.tsv` keeps the addresses where **both** methods agree:

| Column | Meaning |
|---|---|
| `address` | the candidate's address in the executable |
| `kind` | the methods that found it |
| `evidence` | `both` when the two methods agree |

The addresses that only one method found stay in the contributor's local
workspace: they are candidates, and a candidate that no second method
supports is not a function.

## The counts on the pinned target

| Set | Count |
|---|---|
| prologue candidates | 22,592 |
| distinct call targets | 26,280 |
| **both methods agree** | **8,271** |
| union of the two sets | 40,601 |

The call targets are spread over the whole program, including addresses
below the code segment: the retail build calls into thunks and into the
stub area, and the catalogue keeps them apart from the code.

## The third opinion

A disassembler's analysis of the same executable is the third method. It
is not part of the published tooling, because it depends on a tool that
cannot run in the repository's checks; the contributor's recipe is in
`docs/ROADMAP.md`, step 2. When the three methods agree on an address,
the catalogue can call it a *function candidate*; when they do not, the
address stays a candidate, and the difference is what the next wave has to
explain.
