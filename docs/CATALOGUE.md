# The function catalogue

The retail executable is stripped, so the project has no symbol table to
start from. The catalogue is the project's own answer to "where are the
functions?", and it is built from evidence: every address in it carries the
reason why it is there.

The catalogue lives in [`config/functions.tsv`](../config/functions.tsv) and
is generated by [`tools/ppu_funcs.py`](../tools/ppu_funcs.py) and
[`tools/ppu_bounds.py`](../tools/ppu_bounds.py). It holds research
metadata only — addresses and the evidence for them — never game bytes.

## The truth the executable keeps

The PlayStation 3's loader does not jump to the program's code: the entry
point of the executable is the **official procedure descriptor**, a table of
`(function address, global pointer)` pairs that names what every linked
module exports.  On the target it holds 68,490 entries for **34,482
distinct function addresses** — the retail build's own list of its
functions, which survives the strip.

That list is the reference every method is measured against.

## The methods

### The module descriptor (the truth)

`tools/ppu_bounds.py opd` reads the table at the entry point.  It is not
complete everywhere — on *Jak 3* it names 581 procedures out of 19,434
functions, because a module only exports what it exports — but on the
target it is nearly everything.

### The prologue scan

The PS3 SDK's PPU functions open with a fixed shape: the frame is set up
with `stdu r1, -N(r1)` and the link register is saved with `mflr rX`. The
two instructions appear in both orders, and the frame size varies, so the
scanner matches the instruction words, not a fixed byte sequence.

The scan is cheap and it has no false negative on a function that follows
the SDK's shape, but it has false positives, and they are systematic: the
SDK writes the frame setup before *or* after the `mflr`, so a scan that
accepts either order also accepts the **second instruction of a function**.
2,299 of the target's prologue candidates are exactly that.

The link register is saved in **any** general register, so the scan has to
match all of them: a mask that only clears the low three bits of the
register field sees 22,592 candidates instead of 24,224, and misses the
1,632 functions that keep the link register in `r8` or above.

### The call scan

Every `bl` names an address the program calls. The scan collects the
targets, which gives a second opinion about where the functions are — and
it also shows its own weakness: the compiler generates calls to *blocks*
inside a function (shared epilogues, jump-table targets), so a call target
is not necessarily a function start. 245 of them are not.

### The flow bounds (the third method)

`tools/ppu_bounds.py functions` recovers the boundaries from the **control
flow** instead of from the opening of the function.  It walks from the
entry point, the call targets and the first instruction of the code,
stops on the terminals (`blr`, `beqlr`, a sibling branch to a known
function or over another function's opening, the cases of an inline jump
table), and ends a walk when it reaches an address another function
already owns.  The prologue is never used to *find* a function — only read
afterwards, to describe a boundary the flow has already delimited.

Two decoding traps had to be met: the link-register selector is `BF`
(bit 10), not `BI`, or all 608 `bctr` of the target are taken for returns;
and the frame setup comes before or after the `mflr` (see above).

## What is published

`config/functions.tsv` holds the addresses the module descriptor confirms:

| Column | Meaning |
|---|---|
| `address` | the function's address in the executable |
| `kind` | the methods that found it |
| `evidence` | `all` when more than one method agrees |

## The counts on the pinned target

| Set | Count |
|---|---|
| **module descriptor (the truth)** | **34,482** |
| flow bounds | 31,512 |
| prologue candidates | 24,224 |
| distinct call targets | 15,328 |
| the two cheap methods together (the catalogue before) | 8,271 |
| a disassembler's independent sample | 106, of which 105 are call targets |

## The methods measured against the truth

On the target, with the module descriptor as the reference:

| method | found | correct | false | missed | precision | recall |
|---|---|---|---|---|---|---|
| prologue scan | 22,592 | 20,293 | 2,299 | 14,189 | 89.8 % | 58.9 % |
| call scan | 14,566 | 14,321 | 245 | 20,161 | 98.3 % | 41.5 % |
| prologue + call (the old catalogue) | 8,271 | 8,271 | 0 | 26,211 | 100.0 % | 24.0 % |
| **flow bounds** | 31,512 | 31,507 | 5 | 2,975 | **100.0 %** | **91.4 %** |

Ten reference executables built with the same compiler family as the
target give the flow method **100 % precision and 100 % recall**, against
2 to 21 % of recall for the two cheap methods together.

Against the published catalogue of 8,271 addresses, the flow method
confirms 8,202, invalidates 17, leaves 52 uncovered and adds 23,310.

## The third opinion

A disassembler's analysis of the same executable is an independent method.
It is not part of the published tooling, because it depends on a tool that
cannot run in the repository's checks; the contributor's recipe is in
`docs/ROADMAP.md`, step 2.

### The first cross-check

A headless analysis of the rebuilt ELF (Ghidra 12.1.3, the
`PowerPC:BE:64:default` language) was run over the whole executable. It
found 106 functions, and the comparison with the two cheap methods is
this:

| Relation | Count |
|---|---|
| Ghidra's functions that are call targets | 105 |
| Ghidra's functions that are prologue candidates | 41 |
| Ghidra's functions in neither set | 1 |

The call scan covers every function the disassembler found but one, which
is the strongest result the catalogue had: the two methods agree with an
independent analysis almost everywhere, and the address they disagree on
is the one to look at first.

The disassembler's own coverage is small — it analysed the executable's
code far less thoroughly than the scans do — so its 106 functions are
a *sample*, not a limit. Its value is that it is independent, and it
agrees.

## What is still missing

The flow method misses the functions that follow a call that never
returns (17 cases on the target) and the cases of jump tables that are
written in memory rather than inline (260 of the target's 608).  Both are
known, bounded and measured.
